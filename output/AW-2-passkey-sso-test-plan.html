1. Scope and objectives

Objective: Verify that the VWO login page presents the SSO and Passkey options in the specified order; successful authentication reaches the dashboard; failures and unsupported environments give appropriate guidance; and authentication uses secure protocols without exposing sensitive data in the UI or network logs.

In scope

  • Visibility and placement of "Sign in using SSO" and "Sign in with Passkey" below "Sign in with Google".
  • Successful and failed SSO authentication, including each configured identity provider.
  • Successful Passkey authentication when a registered passkey is available and verified.
  • Passkey-unavailable, authentication-failure, and unsupported-browser/device feedback.
  • Compatibility across the product-approved browser/device support matrix.
  • Use of the applicable OAuth, SAML, or WebAuthn protocol and checks for sensitive-data exposure in UI and network logs.
  • Focused regression checks for existing login options, based on the ticket's "alongside existing authentication methods" statement.

Out of scope until clarified

  • Identity-provider configuration or behavior outside the VWO integration boundary.
  • Passkey enrollment, account recovery, account linking, or changes to existing authentication policy; AW-2 does not define these flows.
  • Performance, accessibility, localization, and security certification targets not specified in AW-2.

6. Test data and environment

  • Data: Request valid and invalid SSO test accounts for every configured provider; an account with a registered passkey; an account with no available passkey; and a controlled failed-verification case. The ticket does not supply these accounts or setup steps.
  • Environment / flags: Use a product-approved QA environment with SSO providers and Passkey support configured. Environment URL, flags, provider configuration, and browser/device matrix are pending.
  • Roles / permissions: Role and account eligibility rules are unspecified. Use only product-approved test identities; confirm required roles/account states with the author.
  • Evidence: Capture outcomes and sanitized logs only. Do not store credentials, passkey secrets, tokens, or other sensitive values in test evidence.

7. Risks and assumptions

  • Assumptions: "Dashboard" means the product-approved post-login destination. This plan does not assume a particular URL or redirect policy.
  • Assumptions: The configured identity providers and supported browser/device list will be supplied by the product team before execution.
  • Risk: Missing provider, test-account, and support-matrix details can leave authentication paths untested or produce inconsistent results.
  • Risk: Vague security and error requirements can prevent objective release sign-off.
  • Risk: Test logs or evidence could expose sensitive values if approved capture and redaction rules are not defined.

8. Entry and exit criteria

Entry

  • QA build and environment are available; the feature is enabled as intended for that environment.
  • Product confirms configured identity providers, supported browser/device matrix, test accounts, expected errors, and dashboard destination.
  • Security and privacy owners define protocol mapping and safe log/evidence inspection guidance.

Exit

  • All approved P0 and P1 scenarios pass; failures are documented and triaged by the QA/product owner.
  • Every configured provider and approved supported Passkey environment has recorded results.
  • No unresolved critical authentication or sensitive-data exposure defect remains. The responsible QA owner approves any accepted residual risk.
  • Human review resolves or explicitly accepts the open questions before the plan is used for release sign-off.
